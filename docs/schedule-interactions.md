# Schedule pointer changes and Undo

Moving and resizing tasks use five-minute pointer snapping. Moving keeps the point where the block was grabbed and preserves its duration, including when clamped before midnight. The preview shows the proposed date, both times and duration. Recurring moves and resizes use the original logical occurrence date and label the preview “This occurrence.” The resize grip is larger without taking over the entire block.

Pointer saves use `schedule_change` through the existing task-list transaction and shared application save queue. They validate task location, current scheduling fields, completion and recurrence state instead of optimistically modifying a task and rolling back an entire task after a failure. Initial planner creation rechecks the original scheduling guard after the asynchronous initialization. A changed account or planner clears pending feedback and ignores stale responses.

Confirmed changes offer Undo for ten seconds after the response arrives. The source receipt contains the prior scheduling fields, including absent legacy fields, and the post-save guard. `schedule_undo` validates the original click’s time window and consumes that receipt in the same transaction; waiting in the shared save queue cannot expire a click made in time. Undo preserves unrelated notes, checklists, reminders and focus edits, and refuses later schedule, status, template or location changes. A recurring Undo restores only the selected occurrence’s scheduling override keys and preserves its other exception data and every other occurrence. Explicit overrides remain present for flexible occurrences scheduled at their template’s own times. Ordinary backlog tasks retain their last scheduled duration when it differs from the effort estimate.

Unconfirmed saves and Undo show Retry and Dismiss. Retry retains the exact original operation identity so a lost response can be reconciled without applying the change twice. Dismiss clears the request’s feedback; it does not claim that an uncertain save failed. These short-lived requests are held in the current page only. Reloading reads the saved planner as usual and does not reconstruct a pending pointer request.
