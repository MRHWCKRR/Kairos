# Focus time linked to tasks

The existing dashboard timer and a shared timer bar now use one controller. Start focus from an ordinary task or assignment session in Tasks details or the Schedule inspector. The editors show planned minutes and logged seconds; an assignment rolls up its own logged time plus retained linked sessions, including archived sessions. Planned assignment minutes count active linked sessions, including completed sessions. Logging time never adjusts estimates or automatically completes a parent assignment.

Pause/Resume preserves elapsed time. **Log time** saves time without changing completion; **Log and complete** saves time and marks the selected ordinary task complete in the same Firestore transaction. General focus remains available on the dashboard and contributes only to overall totals. The bar stays available when switching pages. Existing task notes/checklists and editor draft guards are preserved. Recurring tasks offer focus from dated occurrence views, as described below; series templates do not offer it.

## Persistence and recovery

A local record scoped by account retains the captured planner, task ID/location/assignment identity, accumulated milliseconds, checkpoints and any pending log. Every running second checkpoints locally. Page exit pauses synchronously; crash/reload recovery uses only the last checkpoint and stays paused. Resume is explicit. A single log is limited to 24 hours, after which the timer pauses. The browser must provide persistent local storage and Web Locks for safe shared-tab control; unavailable recovery storage prevents starting rather than silently losing work. Web Locks coordinate tabs in the same browser profile, not independent devices.

The immutable pending request is saved before the cloud transaction. Uncertain results retain the exact ID, duration, target and mode across reload/retry. Starting another session cannot replace active/pending work. Discard is confirmed and unavailable while an uncertain save may already have committed. A known pre-commit unavailable target can fall back to Log time; expired receipt history can be reviewed and discarded without replaying old time. Account switches isolate records and late callbacks cannot clear another account's timer. Logging to a captured planner requires that planner to remain active in the app.

## Additive data

- Task `focusLoggedSeconds`: cumulative seconds attributed to that ordinary task. Archive preserves it; deleting a task removes its task-level total. Overall user time remains retained.
- User `focusData`: existing total, longest session and daily focus log, updated from authoritative values. The profile timezone determines the log's end-day; absent profiles use the browser timezone. A session crossing midnight is attributed to its log end-day, as with the previous timer.
- User `focusLogReceipts` and `focusLogReceiptFloor`: atomic retry receipts, bounded to 100 entries/64 KiB. A matching retry returns its original result without writing again. Evicted logs cannot be replayed. No collection migration or additional Firestore listener is needed.

The transaction reads both the user and owned planner before writing. Log and complete never completes an archived, missing, ambiguous, moved/reassigned target or an undated recurring-series template. Log time can retain such a session in overall user totals with no task attribution. Content and unrelated metadata stay intact. Existing task-count statistic saves write only their own daily task counts so they cannot overwrite a newer focus total. Completion achievement feedback uses the existing confirmed-completion path.

Verification covers clock/recovery, local storage failures, concurrent tabs, account changes, receipt eviction, exact retries, moved/deleted targets, metadata preservation, stats concurrency and both editor entry points. Browser QA exercises the actual app focus adapters/controller/store with mocked Firebase transport and controlled time; live verified-account writes remain outside that test.

## Recent focus history and corrections

Open **Focus history** beneath the dashboard timer. Search by the original date, captured task title or assignment title. Correct a duration with minute/second inputs, or confirm removal of an accidental log. A correction is limited to 1 second–24 hours; removal records zero seconds and hides the row. Completion, checklists, estimates, task counts and parent completion never change through this path.

New logs append `focusHistory.sessions` to the existing account document. History begins with this update; old receipt data is not reconstructed because it does not retain the original timezone day. The latest 100 entries are retained, with earlier eviction if the initial history payload exceeds 64 KiB. Corrections add bounded operation metadata per retained entry. Removed rows retain a tombstone until eviction. Eviction never subtracts time: older sessions and pre-update totals remain in the aggregates. `focusHistory.baselineLongest` retains the longest session outside editable history so correcting/removing a recent record can accurately recalculate the displayed longest session.

Corrections read the account and original owned planner in one transaction, then apply a signed delta to overall time, the stored original end-day and the uniquely identified task when retained. Task moves and archives preserve correction support; deleted tasks leave only the overall correction. Ambiguous IDs or inconsistent counters reject without partial writes. The original planner must be selected before correcting a planner-linked session. No new collection, security rule or listener is required; account deletion removes history with the existing user document.

Each correction captures an expected session revision and unique operation ID. The last edit fingerprint reconciles an exact lost-response retry; stale revisions cannot apply another delta. Before any save, the browser stores the immutable request under the account's recovery key. Reload and uncertain failures retain **Retry correction**. Browser Web Locks and checking existing recovery records prevent another tab replacing pending work. Account switches close private history and isolate late responses. Older totals outside recent history remain visible in statistics but cannot be edited individually.

## Remaining-work check-in

When ending an ordinary task or assignment-session timer with **Log time**, the timer pauses and offers three outcomes before saving: keep the current estimate, set remaining work, or explicitly mark complete. Back/Escape returns to the paused, unlogged timer. General focus, completed tasks and parent assignments with retained child sessions keep their existing logging flow. The existing **Log and complete** control remains an explicit shortcut. Parent assignment work is estimated through its linked sessions rather than an independent parent override.

The optional task `remainingMinutes` field accepts whole minutes from 1 to 1440. It is separate from both original estimates and scheduled duration. Logging time never automatically subtracts from it; zero is not an implicit completion request. Task and assignment summaries show remaining estimates, and AI context includes the explicit value. Existing tasks without the field fall back to their planned duration. No data migration or new collection is required.

The chosen estimate and logged time save in the same existing transaction. A captured work snapshot prevents overwriting an estimate, completion status, membership or schedule changed while the dialog was open. Stale check-ins fail before either time or estimate is saved; users can review again or keep the estimate. The immutable pending log includes the choice across lost-response retries/reload. Repeated finish clicks cannot create competing dialogs, and account/planner changes, page exit or disposal cancel an open prompt while preserving paused recovery.

Assignment progress, deadline impact/capacity, shared planning and carryover previews use remaining work. Saved calendar occupancy and daily booked-work calculations continue using actual block durations until a reviewed planning change is applied. Locked blocks shorter than remaining work require review. Planning signatures include the field, so changed estimates invalidate old previews. Session-effort revisions reset an existing explicit estimate to the reviewed amount; planning Undo captures and guards that field as part of those changes. Focus-history duration corrections remain time-only and never rewrite remaining estimates or completion.

## Focus on recurring occurrences

Open a dated recurring occurrence in Tasks details or Schedule and choose **Start focus**. Series templates do not offer a focus target. The timer captures the series ID, original logical occurrence date and recurrence-rule signature. A moved occurrence keeps its original identity; the displayed date may differ. Fixed and flexible occurrences support Log time, the remaining-work check-in and explicit Log and complete. These actions do not change the series template, its checklist, other dates, or calendar placements. Completion uses the existing occurrence exception status and a `seriesId::date` completion identity.

Occurrence `focusLoggedSeconds` and `remainingMinutes` live directly in `recurrence.exceptions[logicalDate]`, alongside existing status/override metadata. Generated occurrences expose their own values, defaulting to zero logged seconds and their effective duration; they never inherit template focus time or remaining estimates. A duration override on a flexible occurrence supplies the check-in's fallback estimate. The additive fields need no migration, listener or security-rule change. Existing ordinary timers and receipt payloads remain valid.

The owned-planner transaction validates the active unique series, captured location, recurrence signature and generated occurrence before attributing time. Skipped/deleted/missing occurrences, changed rules and archived/moved series cannot be completed or have remaining work changed by a stale timer. Log-only can retain the time in overall totals without attribution. The chosen occurrence metadata survives paused recovery and exact pending retries through the same account-scoped timer record.

History rows retain the logical occurrence date and captured displayed date, support date searches, and correct only that occurrence's raw time ledger plus overall/original-day totals. Corrections preserve status, completion timestamps, checklist overrides and remaining work. Missing series/ledgers allow only the overall correction, never a guessed write to another date or the template. When splitting a series, the original retains future dated time-ledger entries for corrections even though those dates fall outside its shortened rule; the new series starts with fresh exceptions and receives no copied focus totals or remaining estimates. Account deletion uses the existing user/planner cleanup.
